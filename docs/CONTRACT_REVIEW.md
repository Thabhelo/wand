# Phase 0 review packet

**Approved with eight user amendments on 2026-09-20.** Those amendments are incorporated below. Phase 1 is authorized; no further contract approval is pending.

## Security and protocol resolutions

1. **Locked means private.** get_state while locked returns exactly `{"screen_locked":true}`. lock_screen while already locked succeeds with exactly `{"already_locked":true}` without invoking the OS lock operation. A newly completed lock returns `{"already_locked":false}`. Every other action returns `device_locked`. Unknown lock state returns `lock_state_unknown` and executes nothing. Recheck immediately before each execution, for both local and relay commands. No unlock endpoint exists.
2. **Pairing has two different authorities.** `POST /v1/pairing/code` is unauthenticated but rate limited, returning a 10-minute code and independent random 256-bit bootstrap token. The token is stored in Keychain, its SHA-256 hash in pairing_codes. Authenticated `POST /v1/pairing/claim` atomically assigns the pending device to the claiming user. Code is single-use; neither the code nor bootstrap token authorizes commands.
3. **Durable handoff without raw token storage.** The agent generates a 32-byte CSPRNG token, base64url without padding, saves it in Keychain, then calls `POST /v1/pairing/redeem` with bootstrap bearer auth and `{device_token}` body. Until claim: 409 pairing_pending. After claim: atomically activate token hash and set redeemed_at. Lost responses may retry the identical token with the same unexpired bootstrap secret; a different token conflicts. Never permit a redeemed bootstrap to reactivate a revoked device. Poll redemption every 3 seconds with uniform ±0.5s jitter, never overlapping requests. Stop at code expiry; invalidate the bootstrap secret, clean pending records, and restart enrollment while the pairing view is active. Do not run enrollment loops after the view closes. No pairing token in URLs, analytics, access logs or traces.
4. **No silent command queue.** POST returns 202 dispatched only after socket send succeeds. A missing live authenticated socket returns 409 device_offline. `last_seen` is nullable for never-seen devices. Error context is inside the standard `error` object.
5. **Delivery and deadline.** Agent sends `delivered` after validation and before executing. Added `expires_at` is server creation time +15s. Relay timer begins at dispatch; timeout becomes failed/command_timeout with wording “Outcome unknown; check before retrying.” Expiry does not guarantee cancellation of an OS action already started. Do not replay on reconnect or automatically retry non-idempotent actions. Agent rejects command_expired on receipt and again immediately before execution if expires_at is more than 5 seconds in the past. Reject expires_at more than 20 seconds in the future as invalid_deadline; this limits replay windows but cannot authenticate an honest timestamp from a compromised relay. Persist the command ID before execution. Deduplication retains the newest 10,000 entries or entries younger than 10 minutes, whichever fills first; prune at age >=600s and evict oldest at capacity. Duplicates return duplicate_command without executing. Persistence failure fails closed. Clock rollback and eviction limit replay protection; a compromised relay can still mint new IDs. Unknown, wrong-device, duplicate and late results cannot change terminal status.
6. **Heartbeat and revocation.** Every 25s; close/offline after 75s without valid heartbeat, immediately on disconnect. Rate-limit failed hello attempts to 10/minute/IP; reject further connections for the remainder of the fixed window, with bounded limiter storage. Authenticate hello within 5s; hash comparison and revoked status checked before registry insertion. One active connection per device, generation-fenced so an old connection cannot mark a replacement offline. On relay restart clear stale online flags; terminate nonterminal commands as outcome unknown. Revocation persists first, then sends revoke and closes socket. A reconnect rejection with WS close code 4003 means revoked: delete Keychain device token and return unpaired. Backoff with full jitter, cap 60s. A partitioned Mac cannot learn revocation within 30 seconds; enforce immediately at relay and on next successful contact. The 30s UI promise applies to connected devices only.
7. **E2EE reservation.** Optional encrypted_payload is null-only in v1. Non-null payloads fail closed. Future encryption requires negotiation and a new protocol contract; do not suggest that this placeholder encrypts anything.
8. **Data and audit.** Append one audit event at dispatch and one at terminal result, with action, principals, IDs, IP and timestamp. Offline attempts with known owned device also get failed audit events. Never store state contents or shortcut names in relay audit/logs/traces. The Mac local log MUST retain full validated action params and status, including URL and Shortcut name, as the forensic source; never store bearer tokens or get_state payloads. Keep local logs on the device with owner-only permissions, 90-day retention, a 10 MiB cap (oldest-first eviction), and user-controlled clear/export. Disclose that local logs may contain sensitive URLs and names. Persist params_json as `{redacted:true}` for all actions; validate original params in memory before dispatch. State results live in memory for polling up to 60 seconds, then return result_expired (410). Retain other command metadata and audits 90 days, aggregate only nonidentifying counts, then purge. User deletion overrides retention. Append-only means application cannot edit events; a tightly scoped retention/deletion role may remove them. Database owner compromise defeats this assurance.
9. **Consent and extensibility.** Approval metadata is a UX layer over audit/rate limits, not a security boundary or proof of user confirmation. V2 requires explicit out-of-band step-up approval on a second device/push for high-risk actions, bound to user, device, action, params digest, expiry and a single-use nonce. Reserve AuthorizationContext.oauth_client_id and allowed_actions now; derive from verified token claims and server policy, never command request fields. Persist oauth_client_id in commands/audit. MVP admits only the configured Meta client; adding another OAuth client requires per-client action scoping and denial by default. A future approval grant must be separate from the chat request and independently verified by the agent; it is not implemented in v1. A malicious OAuth client or compromised relay can issue allowlisted actions without conversational consent. Local Shortcut allowlisting authorizes the whole Shortcut, which may itself execute shell scripts; MacBridge exposes no arbitrary-shell action but cannot honestly promise Shortcuts cannot run code. Match names exactly, pass Process argv, never interpolate into AppleScript source or shell strings.

## REST inventory for implementation

All responses JSON. All public routes use user OAuth bearer except bootstrap routes and health. Device and command lookups are ownership-scoped; use 404 for another user's resources. Enforce 60 commands/minute/user and 10/second/device; pairing claim 5/minute/IP, plus issuance/redemption throttles. Only trust client IP from explicitly trusted proxies.

| Method and path | Request → success | Additional failures |
| --- | --- | --- |
| GET /healthz | none → 200 `{status:"ok"}` | 503 unavailable |
| GET /v1/devices | none → 200 DeviceList | 401 |
| POST /v1/commands | CommandRequest → 202 CommandAccepted | 400,401,404,409 device_offline,429 |
| GET /v1/commands/{command_id} | none → 200 CommandStatus | 401,404,410 result_expired |
| POST /v1/pairing/code | PairingCodeRequest → 201 PairingCodeResponse | 400,429 |
| POST /v1/pairing/claim | PairingClaimRequest → 200 PairingClaimResponse | 400,401,409 pairing_unavailable,429 |
| POST /v1/pairing/redeem | bootstrap bearer + PairingRedeemRequest → 200 PairingRedeemResponse | 401,409 pairing_pending/token_conflict,429 |
| PATCH /v1/devices/{device_id} | RenameDeviceRequest → 200 Device | 400,401,404 |
| DELETE /v1/devices/{device_id} | none → 200 RevocationResponse | 401,404 |
| DELETE /v1/account | none → 200 `{status:"deleted"}` | 401 |

Local API: 127.0.0.1 only, separate Keychain bearer, POST /v1/commands `{action,params}` and GET /healthz. Reject browser Origin requests and unexpected Host values; no CORS. Same catalog, validation, lock guard and log path as socket execution. Loopback HTTP is the intentional TLS exception; all network traffic uses HTTPS/WSS with certificate validation. Set body/message limit 64 KiB. Local revoke first disables command execution and persists a non-secret revocation-pending marker. Connected agents send revoke_self over the authenticated socket before closing; the relay atomically revokes all tokens for that socket device, returns revoke, then closes with 4003. No target device ID is accepted. Local token deletion is unconditional; clear the pending marker only after revoke/4003 acknowledgment or verified dashboard completion. Wait at most 5s for acknowledgment; send success alone is not proof of revocation. Offline or unacknowledged revoke displays a blocking, persistent warning: "Server-side revocation pending, complete it in the web dashboard," linking to the configured HTTPS dashboard device page with only a device ID. The UI must not claim fully revoked or permit re-pairing until resolved. Never embed tokens in the link.

## Account deletion cascade and incident response

DELETE /v1/account first marks the account as deleting and denies new claims, redemptions and commands. In one transaction revoke every device/bootstrap token, cancel pending commands and detach every device session from routing. Send revoke and close all associated sockets with code 4003 so reachable agents wipe Keychain and unpair. Then purge user, device, token, pairing, command and audit records, overriding the 90-day retention. Socket-delivery failure does not roll back revocation; disconnected agents learn on reconnect (all unrecognized formerly issued tokens also receive 4003). Return deleted only after the durable cascade/purge completes; retries are idempotent. Backups must expire within a documented maximum and restored data must reapply deletion before service resumes. Hosted-identity deletion must also be implemented or explicitly disclosed as separate; removing local credentials on offline Macs cannot be guaranteed by this endpoint.

Incident response: immediately revoke compromised credentials, correlate relay user/device/command IDs and timestamps with full parameters in the Mac's local log, and export that local evidence with user consent. Relay audit can establish that open_url ran but cannot recover which URL it opened. If the Mac/log is lost, deleted, capped, or compromised, that forensic detail may be unrecoverable and local entries are not tamper-proof. Do not quietly collect it in cloud diagnostics to compensate. Full params stay local; state payloads and bearer tokens are never forensic log fields.

## Phase 1 empirical blockers

- Verify WebSocket sleep/wake behavior: on sleep proactively suspend/disconnect, mark offline on close or at the 75s heartbeat deadline if no close arrives; wake creates a fresh generation and never replays commands. A stale pre-sleep receive loop cannot execute after wake. Test this on both macOS releases.
- Test actual CGSession availability and lock detection on both macOS releases; no guessed fallback keypress.
- Verify Safari and Chrome pinned-tab detection without collecting URLs/window titles. If pinned status cannot be determined, fail without closing tabs.
- Verify DND setter support; do not edit private preference databases or silently invoke an unapproved Shortcut.
- Verify graceful quit behavior with unsaved documents; refusing/cancelled quit is failure, never force kill.
- Verify Music/Spotify automation and choose deterministic player precedence.
- Verify app-name resolution: ambiguity must fail, not open an arbitrary match.
- Verify shortcuts argument handling for leading dashes and metacharacters, exact allowlist matching, timeouts and lock checks.
- App signing, notarization and real deployed acceptance need Apple Developer and hosting configuration. None configured or claimed yet.
